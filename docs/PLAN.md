# TV Player implementation plan

## Goal

Build a small, dependable native Android TV player for direct video URLs, designed first for Sony BRAVIA and controlled entirely with a TV remote. A browser on a phone or computer can make link entry easier, but it does not proxy, download, or stream video: the Android TV device fetches the submitted video and subtitle resources and plays them.

The working product name is **TV Player**. Choose a new package/application ID during the first implementation milestone; do not reuse Seedr's identity or credentials.

## Product boundaries

- Native Android TV app in Kotlin, using Compose for TV for the interface, AndroidX Media3 ExoPlayer for playback, and DataStore for small persistent settings and history. Confirm compatible library versions and platform requirements when scaffolding.
- The current source configuration uses minimum Android API level 26, compile/target API 36, and pinned Compose for TV/Media3 versions. The pinned build passed on the local toolchain and the package installed on BRAVIA VU3; target-device runtime compatibility remains unverified.
- Support direct HTTP(S) video URLs that the TV can access and Media3 can decode. This is not a general-purpose crawler, cloud downloader, transcoder, or file-hosting service.
- Support external SRT and WebVTT subtitles when compatible with the selected media/player path. Treat subtitle URL credentials as sensitive and avoid persisting authenticated subtitle URLs unless the user explicitly opts into history that stores them.
- Keep all app UI, settings, errors, documentation, and examples in English. Do not add localization, Sinhala UI, or a language toggle. Subtitle content may use any language and Unicode supported by the playback stack.
- Serve a deliberately small local page on the TV for link entry from a phone or laptop on the same Wi-Fi. It submits the video URL and optional subtitle URL to the TV app. The TV then fetches and plays both resources directly.
- Keep the local submission endpoint LAN-only; do not expose it to the public internet or add router/firewall setup. Use a pairing/session token, validate HTTP(S) URLs and request sizes, and avoid logging tokens or full signed URLs.
- Build every primary flow for D-pad navigation. Focus visibility, predictable traversal, menu reachability, and focus restoration after closing overlays are acceptance requirements, not polish items.
- Do not fabricate quality or resolution choices. Show selectable audio tracks or quality variants only when the actual media provides them. Report file pixel dimensions separately from stream/track quality where relevant.
- Seedr integration is an optional later investigation, gated on proving a supported authentication path. It is not a dependency of the initial product or the first milestone; do not copy tokens or credentials from another app.

## Architecture direction

Keep the player screen, playback state, local link-submission server, persistence, and URL/security validation as small separable components. The player owns the Media3 session and TV-side network requests. The local page only sends a bounded request to the TV endpoint; it never relays media bytes. Choose the server lifecycle deliberately so the endpoint is available only while the app is in an appropriate foreground state, and stop it cleanly when no longer needed. Avoid adding a foreground service or broad background playback behavior unless a later product requirement justifies it.

Persist playback position and recent-item metadata locally. Prefer a stable user-facing title/source descriptor and position over storing full signed URLs. Provide an explicit, local opt-in if full source URLs are needed for convenience, and provide a clear-history action. A changed or expired signed URL cannot be regenerated by the app: when the user supplies a replacement URL, offer to resume from the remembered position when the resource appears compatible, while allowing restart. Do not claim exact resume compatibility when the source cannot be identified reliably.

## Release-one acceptance

The first useful release is complete when a user can enter a direct video URL either on the TV or through the same-Wi-Fi submission page, play it on the TV, control playback with the remote, load a compatible external subtitle URL or local SRT/WebVTT file, adjust subtitle and display settings, recover from common errors, and manage private local recent-item/resume data. The link-entry page must not carry media traffic. TV focus and D-pad behavior must be demonstrated on an approved real TV before reporting that acceptance as complete.

## Validation policy

- Run focused build/lint checks and meaningful tests when authorized. Milestones 2–12 were implemented source-only; milestone 13 authorized and completed debug build/lint and package installation without launch. Report exact evidence and remaining runtime checks.
- Emulator evidence is useful for navigation and media plumbing but is not proof of Sony BRAVIA compatibility.
- Real-TV installation, network access, input, playback, subtitle rendering, and focus checks must be recorded separately. Launch, input, navigation, and runtime QA require explicit approval; installation alone is not behavioral evidence.
- Do not claim playback or device behavior based on a successful compile. Record test streams and their actual available tracks/codecs without committing user URLs, credentials, or signed links.
- Do not create a public repository, push, open a PR, or merge unless explicitly requested. If remote publication is later requested, use a PR to `main`.
